## Как устроены все операции

При старте без аргументов программа спрашивает язык (`1. Русский  2. English`, по умолчанию
русский), печатает предупреждение про 3.3 В TTL и показывает главное меню. Любая ошибка внутри
пункта печатается как `[STOP] <причина>` с пометкой «Никаких дополнительных write/erase команд
после этой ошибки не отправлено» и возвращает в меню; порт и лог закрываются.

### Выбор профиля устройства

Почти каждый пункт, которому нужен RAM U-Boot, сначала спрашивает:

```
Профиль устройства:
  1. Auto (определить по UART, если возможно)
  2. Nokia XG-040G-MD / AN7581
  3. Nokia XG-040G-MF / AN7583
```

- **Auto** — SoC определяется по тексту BootROM/DRAM-инициализации (`AN7581DRAMC`, `Airoha AN7581`
  и т. п.). Если текста нет, программа спросит профиль ещё раз, и там уже нужно выбрать MD или MF.
- Если выбран MD, а в UART видно AN7583 (или наоборот) — **стоп**: «UART определил …, но выбран
  профиль …». Это защита от загрузки чужого preloader.

Профиль определяет, какие два файла из `payloads/` будут отправлены. Их размер и SHA256 закреплены
в коде и проверяются перед каждой отправкой.

### Выбор UART-порта

Программа показывает найденные порты:

- **Windows** — только реально существующие `COMn` (через `QueryDosDeviceW`);
- **Linux** — `/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/ttyAMA*`, `/dev/ttyS*`.

Можно ввести номер из списка, имя (`COM6`, `/dev/ttyUSB0`) или на Windows просто число `6` →
`COM6`. Если порт один, Enter выбирает его. Параметры всегда 115200 8N1 без управления потоком.

### Получение RAM U-Boot через BootROM

Общая процедура для пунктов 1–5 главного меню, пунктов 2–5 экспертного режима и RAM U-Boot-режима
Porting Collector. **Во flash ничего не пишется.**

1. Открывается порт, UART пишется в `uart.log` сессии операции (`work/sessions/<id>/`).
2. Подсказка: если на экране уже `Press x to load BL31 + U-Boot FIP` и `CCC` — ничего не
   перезагружать. Иначе: выключить роутер, **зажать Reset, подать питание** (это режим BootROM).
3. До 180 с программа ждёт BootROM. Увидев `Press x`, отправляет `x` (не чаще раза в 2 с). Три
   символа `C` подряд — BootROM готов принять XMODEM.
4. Определяется **стадия приёмника**:
   - *preloader* — обычное начало;
   - *FIP* — если в выводе есть `Press x to load BL31`, `DRAM flow done`, `load BL31 + U-Boot FIP`.
     Тогда preloader повторно **не** отправляется.
5. Проверяется профиль (см. выше) и закреплённые SHA256 файлов.
6. Стадия preloader: XMODEM-CRC отправляет `payloads/<md|mf>/…-preloader.bin`, затем снова ждёт
   `CCC` (до 180 с) и сверяет, что SoC не сменился.
7. XMODEM-CRC отправляет RAM FIP (BL31 + U-Boot RECOVERY_SAFE). Правила XMODEM (подробно — в
   [GUIDE_RU.md](GUIDE_RU.md#xmodem)):
   - блоки по 128 байт, ожидание ACK до 2 с, **не более 8 попыток** на блок; NAK или `C` —
     немедленный повтор только этого блока;
   - одиночный `CAN` — шум линии; отмена приёмником — только **`CAN CAN`**;
   - после ACK последнего блока — EOT с ожиданием 0,9 с; повтор только на явный NAK (до 3 раз),
     на тишину — нет. **Отсутствие ACK на EOT после
     полностью подтверждённых данных не фатально**: успех доказывает следующий этап — второй
     приёмник `CCC` после preloader (шаг 6) или устойчивое приглашение U-Boot после FIP (шаг 8);
   - `CAN CAN CAN` отправляется только при сбое фазы данных, но никогда после ACK последнего блока.
8. Ожидание приглашения U-Boot до 180 с (вывод, пришедший ещё во время EOT, учитывается).
   Как только видно `U-Boot 20…` или `Hit any key to stop autoboot`, программа шлёт Ctrl-C каждые
   250 мс (не более 20 раз); если видит bootmenu — вместо этого только Esc (не более 6 раз).
   **Enter не отправляется**, чтобы не выбрать пункт bootmenu. Приглашение (`AN7581>`, `AN7583>`,
   `U-Boot>`, `=>`) распознаётся по концу потока после удаления ANSI-последовательностей, поэтому
   его видно и после экранного bootmenu. Стоп, если:
   - в выводе `mtd erase ubi` / `Erasing 0x…` — автозагрузка начала стирать NAND;
   - `Starting kernel` / `Booting Linux` — автозагрузка ушла в Linux;
   - после FIP снова `Press x to load BL31` — устройство вернулось в BootROM.
9. Выполняются `version` и `mtd list`. **Проверка геометрии** (без неё стоп): `spi-nand0`, блок
   `0x20000`, min I/O `0x800`, разделы `bl2` = `0x0–0x20000` и `ubi` = `0x20000–0x10000000`.
10. Печатается производитель NAND (Fudan Micro / SkyHigh / неизвестно) — **только для информации**,
    ни на что не влияет.

### Как отправляются команды U-Boot

Каждая команда отправляется кусками по 16 байт (пауза 3 мс) + `\r`, затем программа ждёт
приглашение (`=>`, `AN7581>`, `AN7583>`, `U-Boot>`). После неё отправляется
`echo __URSIDO_<случайное>__RC_$?`, чтобы узнать код возврата. **Код ≠ 0 → стоп.** Если в ответе
команды вдруг видно старт ядра Linux — тоже стоп.

### Передача файла в RAM по TFTP

Используется в пунктах 1–4 и 3–4 эксперта. Порт Ethernet роутера (LAN) соединяется с ПК кабелем.
Подробно об устойчивости — в [GUIDE_RU.md](GUIDE_RU.md#lan-tftp).

0. В самом начале мастера (ещё до выбора профиля и RAM U-Boot) печатается блок **«Сетевые пререквизиты»**: прямой кабель в LAN2/LAN3,
   IP Nokia и ПК, UDP/1069, просьба отключить лишние адаптеры, список активных IPv4-интерфейсов ПК
   (если их несколько — предупреждение, но работа не блокируется).
1. **IP ПК по маршруту.** Берётся адрес интерфейса, через который ОС идёт к `192.168.1.1`;
   запасной вариант — любой активный интерфейс с `192.168.1.x`. Если нет — программа просит
   настроить Ethernet статически (рекомендуется `192.168.1.254/24`) и ввести адрес; проверяет, что к
   нему можно привязаться.
2. **Сеть U-Boot настраивается один раз за сессию:** `ethaddr=02:00:00:04:0d:10`,
   `eth1addr=02:00:00:04:0d:11` (временные локально администрируемые MAC, только в RAM-окружении),
   `ipaddr 192.168.1.1`, `serverip <IP ПК>`, `netmask 255.255.255.0`, `tftpdstp 1069`,
   `autoload no`. Все части большого образа переиспользуют эти настройки.
3. Для каждой передачи — не более **3** попыток:
   1. **встроенный TFTP-сервер** поднимается на `<IP ПК>:1069/UDP` — отдаёт ровно один файл под
      одним ожидаемым именем и только клиенту `192.168.1.1`; все его ожидания ограничены по времени;
   2. `tftpboot 0x90000000 <имя>`; число переданных байт должно совпасть с размером файла;
   3. **проверка в RAM:** `hash sha256` (если есть в U-Boot), иначе `crc32`.
4. Если провалилась сама команда `tftpboot` — сервер останавливается и освобождает порт, U-Boot
   **ресинхронизируется** (Ctrl-C до устойчивого приглашения), сеть U-Boot задаётся заново, пауза
   1–2 с, и повторяется **только эта передача**. Если не сошлись байты или проверка в RAM —
   повторяется только передача, без ресинхронизации и без повторной настройки сети. После 3 неудач —
   стоп «TFTP не прошёл после 3 попыток».

`ping` больше не выполняется: доказательство рабочей сети — сама передача и проверка в RAM.
Максимальный размер одной передачи — `0x08000000` (128 МиБ). Большие образы (stock, physical)
режутся на части по 8 МиБ; повторяется только текущая часть, уже записанные в NAND части не
переписываются.

### Проверка после записи

После каждого `mtd write` область в RAM заполняется нулями (`mw.b`), затем `mtd read` читает
записанное обратно и `crc32` сравнивается с CRC32 исходного куска на ПК. Несовпадение → стоп.
Для UBI-томов: `ubi read` в `0x98000000` и `crc32`.

### Фразы подтверждения

Перед первой записью программа показывает, что именно будет сделано, и требует ввести фразу
**точно**, с учётом регистра. Фразы одинаковы для обоих языков:

| фраза | пункт |
|---|---|
| `RESTORE STOCK BACKUP` | 1. Восстановление стока |
| `WRITE FIP` | 2. Замена FIP |
| `RESTORE PHYSICAL NAND` | 3. Physical NAND |
| `BOOT RAM ITB` | 4. Запуск ITB из RAM |
| `WRITE UBI VOLUME <имя>` | Эксперт 3 |
| `WRITE RAW BL2 0x<смещение>` / `WRITE RAW UBI 0x<смещение>` | Эксперт 4 |
| `UBI ATTACH` | Портирование → A |

Любой другой ввод — «операция отменена пользователем».

### 1. Восстановить заводскую Nokia из mtd16/all_flash backup

**Зачем:** вернуть роутер к заводской прошивке Nokia (например, после неудачной установки OpenWrt
или для возврата оператору) из бэкапа, снятого MedveFlasher или вручную.

**Что нужно:** бэкап `mtd16` (он же «stock restore span», первые `0x0EBA0000` байт NAND: BL2 + вся
заводская область), UART, Ethernet-кабель.

**Шаги:**

1. **Источник.** Путь к *каталогу бэкапа MedveFlasher* или к *файлу*. В каталоге ищется
   `mtd16.bin.gz`, `mtd16_*.bin.gz`, `mtd16.gz`, `mtd16.bin`, `mtd16_*.bin` (первый по алфавиту);
   печатается, сколько из `mtd0…mtd16` найдено. Если рядом есть `SHA256SUMS`/`SHA256SUMS.txt` с
   записью для выбранного файла — хеш проверяется, несовпадение → стоп.
2. **Разбор без записи.** Файл (gzip распознаётся автоматически) читается целиком и режется в
   `stock-<время>/` внутри сессии: `stock-bl2.bin` (первые `0x20000`) и `stock-ibu-NN.bin` (по 8 МиБ).
   Проверки:
   - несжатый размер должен быть **ровно** `0x0EBA0000` байт (больше/меньше → стоп);
   - **происхождение BL2:** если BL2 бэкапа — это известный OpenWrt preloader AN7581/AN7583 (в том
     числе сдвинутый на `0x800` в контейнере из `FF`), это не заводской бэкап → стоп.
   Печатаются SHA256 всего `mtd16`, SHA256 BL2 и число частей.
3. **Профиль и RAM U-Boot** (см. общую процедуру).
4. **Bad-блоки.** `mtd bad bl2` — любой bad-блок в BL2 → стоп. `mtd bad ubi` — bad-блоки внутри
   заводской области разрешены только в «безопасном окне» физических адресов
   `0x052C0000–0x0EB60000`; вне его → стоп («автоматическое восстановление заблокировано»).
5. **Сеть и тест TFTP до записи.** Настройка сети U-Boot, передача первой части и проверка её CRC в
   RAM. Если это не прошло — ничего ещё не стёрто.
6. **Подтверждение** `RESTORE STOCK BACKUP`. Предупреждение: область OpenWrt UBI будет полностью
   стёрта; BL2 пишется последним.
7. `mtd erase ubi` (до 20 мин). Повторный `mtd bad ubi`: карта должна остаться в безопасном окне и
   не потерять ни одного прежнего bad-блока.
8. **Запись частей.** Для каждой части по 8 МиБ: TFTP → RAM (+CRC), затем запись только по
   «хорошим» участкам между bad-блоками (`mtd write ubi …`) с проверкой после записи для каждого
   участка. Если U-Boot пишет `skipping bad block` / `new bad block` → стоп, BL2 не тронут.
9. Третий `mtd bad ubi`: карта не должна измениться за время записи, иначе стоп (BL2 не тронут).
10. **BL2 последним:** TFTP `stock-bl2.bin` → `mtd erase bl2` → `mtd write bl2` → проверка.
11. Итог `Восстановление стока PASS` с SHA256 источника. Enter — `reset`, `N` — остаться в U-Boot.

**Почему BL2 последним:** пока BL2 старый, недописанная заводская область не мешает снова войти в
BootROM и повторить. Сломанный BL2 при недописанном остальном — худший вариант.

### 2. Починить загрузку OpenWrt / заменить FIP

**Зачем:** OpenWrt в UBI цел, но не загружается из-за испорченного/неподходящего загрузчика в
UBI-томе `fip` (BL31 + U-Boot).

**Шаги:**

1. Профиль → RAM U-Boot.
2. `ubi part ubi` — подключение существующего UBI. Не подключился → стоп («ремонт только FIP
   неприменим»). `ubi info layout` — должен быть том `fip`.
3. Выбор источника: `1` — встроенный RAM FIP текущего профиля (рекомендуется для спасения),
   `2` — свой `.fip`. Проверка файла: размер 200 000 байт … 2 МиБ и заголовок TF-A FIP ToC
   (`01 00 64 AA 78 56 34 12`). Печатаются путь, размер, SHA256.
4. TFTP в `0x90000000` + проверка в RAM.
5. Подтверждение `WRITE FIP`. Перезаписывается **только** существующий том `fip`.
6. `ubi write 0x90000000 fip <размер>` → `ubi read 0x98000000 fip <размер>` → `crc32`.
7. Enter — `reset`, `N` — остаться в RAM U-Boot.

> Встроенный RAM FIP — это U-Boot RECOVERY_SAFE: с ним роутер после reset остановится в U-Boot
> (`bootdelay=-1`) и сам ничего не запустит. Это «безопасная площадка» для дальнейшего ремонта, а не
> штатный загрузчик OpenWrt. Для штатной работы используйте FIP из UrsusBoot/UrsusFlasher.

### 3. Восстановить полный physical NAND image (256 MiB)

**Зачем:** залить полный сырой образ NAND (например, снятый программатором или из `all_flash`).

**Шаги:**

1. Путь к образу; размер должен быть **ровно** `0x10000000` (256 МиБ). Печатается SHA256.
2. Профиль → RAM U-Boot.
3. `mtd bad bl2` и `mtd bad ubi`: в 0.2.0-test17 **любой** bad-блок → стоп. Сырой образ содержит
   чужую раскладку bad-блоков; писать его поверх NAND с bad-блоками без понимания формата нельзя.
4. Сеть; образ режется в `physical-<время>/` внутри сессии на `bl2.bin` и `ubi-NN.bin` по 8 МиБ. Первая
   часть передаётся как тест TFTP.
5. Подтверждение `RESTORE PHYSICAL NAND`.
6. `mtd erase ubi`, затем каждая часть: TFTP → `mtd write ubi` → проверка.
7. BL2 последним: `mtd erase bl2` → `mtd write bl2` → проверка.

### 4. Загрузить OpenWrt recovery ITB в RAM

**Зачем:** запустить OpenWrt initramfs (или другой recovery-образ FIT) прямо из памяти, не трогая
flash, — например, чтобы оттуда сделать бэкап или sysupgrade.

**Шаги:**

1. Путь к `.itb`; проверяется магия FIT `D0 0D FE ED`.
2. Профиль → RAM U-Boot → TFTP в `0x90000000` + проверка в RAM.
3. `iminfo 0x90000000` — если недоступен или ошибся, только предупреждение (магия уже проверена).
4. Подтверждение `BOOT RAM ITB`, затем `bootm 0x90000000`.
5. 60 секунд вывод UART показывается и пишется в лог; затем возврат в меню. Ctrl+C на ПК в роутер
   здесь **не** передаётся. Дальше работайте через терминал (Эксперт → 1) или по сети.

### 5. Диагностика NAND / UBI / U-Boot

**Зачем:** посмотреть состояние NAND перед ремонтом или для отчёта.

1. Профиль → RAM U-Boot. Печатаются профиль и производитель NAND.
2. `mtd bad bl2`, `mtd bad ubi` — списки bad-блоков.
3. `mtd list` — разметка MTD.
4. Сообщение «UBI attach пропущен»: обычная диагностика **не** отправляет `ubi part`, потому что
   attach может изменить метаданные UBI или fastmap. Для намеренного attach есть отдельный
   ADVANCED-режим — Портирование → A или `probe --ubi-attach`.
5. `printenv` — окружение RAM U-Boot.

Диагностика полностью только читает: write, erase и attach NAND/UBI не выполняются (с test14;
до этого она выполняла `ubi part ubi` + `ubi info layout`).

### 6. Собрать пакет логов для отчёта

Создаёт `UrsidoRescue-support-<дата-время>.zip` рядом с программой. Внутрь попадают все `*.log` и
`*.txt` из `work/` (UART-логи всех сессий) и `VERSION`, `STATUS.md`, `BUILDINFO.json`,
`MANIFEST.json`, если они есть. Порт не открывается.

> UART-логи содержат вывод U-Boot/Linux и могут включать MAC и серийный номер. Перед публикацией
> просмотрите архив.

### 7. Портирование / исследование оборудования

Porting Collector — **только чтение**. Его задача — собрать о незнакомом Airoha-устройстве всё, что
нужно для порта UrsusBoot и профиля UrsusFlasher. Полное описание правил безопасности и собираемых
данных — в [../PROBE.md](../PROBE.md). Кратко:

- каждая команда проходит **allowlist** (`probe/guard.go`) и перепроверяется прямо перед отправкой;
  `erase`, `write`, `saveenv`, `env save`, `ubi create/remove/write`, `sf write/update`, сокращения
  команд U-Boot, `;`, `&&`, `|`, `$`, кавычки не отправляются никогда; `--unsafe` ничего не
  ослабляет;
- неизвестному загрузчику ничего не отправляется, пока не увиден баннер U-Boot или загрузки Linux;
- MAC/серийники/GPON не попадают в `profile.json`, отчёт и черновик — там только *где* они лежат.

```
 ПОРТИРОВАНИЕ / ИССЛЕДОВАНИЕ ОБОРУДОВАНИЯ
  1. Исследовать новое устройство Airoha (полный автоматический probe)
  2. Собрать профиль BootROM
  3. Собрать профиль U-Boot
  4. Собрать профиль Linux
  5. Собрать карту flash / MTD / UBI
  6. Собрать DTB / device tree
  7. Собрать данные сети / PHY / коммутатора
  8. Экспортировать porting bundle Ursus
  9. Показать собранный профиль
  A. ADVANCED: U-Boot UBI attach (НЕ read-only)
  N. Начать новую probe-сессию (текущая: …)
  0. Назад
```

Все сборы пишут в **текущую probe-сессию** — каталог `work/sessions/<дата>-<время>-probe-<hex>/`. Несколько
пунктов подряд дополняют одну сессию; `N` начинает новую.

Пункты 1, 3–7 сначала спрашивают: *«Устройство уже включено и стоит в U-Boot/Linux prompt (разрешить
один Ctrl-C)? [y/N]»*. `y` = режим `--wake`: один Ctrl-C, чтобы разбудить уже работающее устройство.
Затем программа напоминает: flash-команды probe только читают, а stock LAN assist сначала лишь
читает реквизиты Web; если понадобится включить FTP, будет отдельный вопрос `y/N`. Таймаут —
5 минут.

**Вход в stock Linux.** Если на UART появился stock `Login:` Nokia XG-040G-MD/MF, probe сначала
пробует **stock LAN assist**:
1. берёт актуальные реквизиты через Web `192.168.1.1` (ожидание до 90 с);
2. входит по UART под UID0-сервисной учёткой или через Telnet-учётку и `su`;
3. проверяет `id -u` = 0;
4. если UID 0 не подтверждён, 12 секунд продолжает читать UART, один раз перечитывает Web-реквизиты
   и повторяет вход/`su`;
5. только после этого, если FTP выключен, спрашивает `y/N` о его включении.
Для этого ПК должен быть в сети `192.168.1.x` и подключён кабелем к LAN роутера. Пароли остаются
только в памяти. Подробно — в [GUIDE_RU.md](GUIDE_RU.md#stock-login). Если assist не сработал,
логин и пароль спрашиваются вручную.

| пункт | что собирает |
|---|---|
| **1. Полный probe** | Все слои: BootROM-маркеры, U-Boot, flash/MTD/UBI, DTB, сеть, GPIO, Linux. Сценарий: включите устройство → probe прерывает автозагрузку U-Boot и собирает данные → просит перезагрузить устройство (Reset **не** держать) → ждёт Linux, не прерывая его, и собирает Linux-часть. В конце автоматически делается экспорт bundle. |
| **2. Профиль BootROM** | Подменю, см. ниже. |
| **3. Профиль U-Boot** | Только U-Boot: `version`, `help`, `bdinfo`, `printenv`, `mtd list`, `mtd bad`, `nand/mmc info`, `dm tree`, `mii`/`mdio`, `gpio status`, control DTB. |
| **4. Профиль Linux** | Только Linux: `uname`, `cpuinfo`, `cmdline`, `meminfo`, `/proc/mtd`, `/sys/class/mtd`, `ubinfo`, `dmesg`, `fw_printenv`, `board.json`, `/sys/firmware/fdt`, `ip link/addr`, `ethtool`, debug gpio. На stock `Login:` — сначала stock LAN assist (см. выше); если он не сработал, включается ручной fallback: probe спросит логин и пароль, и только там пустой логин означает пропустить Linux-часть. |
| **5. Flash / MTD / UBI** | Карта разделов и сэмплы: первые 4 КиБ каждого раздела и последние 4 КиБ разделов до 8 МиБ (`mtd dump`), геометрия UBI из заголовков EC/VID, разбор FIP ToC, SHA256 загрузочных разделов. Работает в первой доступной среде (U-Boot или Linux). |
| **6. DTB** | Control DTB из U-Boot (`md.b`) или `/sys/firmware/fdt` из Linux; разбирается встроенным парсером в `dt/fdt.dts` (dtc не нужен). |
| **7. Сеть / PHY / коммутатор** | `mii`/`mdio` в U-Boot, `ip`, `ethtool` в Linux. |
| **8. Экспорт** | Анализирует текущую (или последнюю) сессию и пакует `ursus-probe-<vendor>-<model>-<soc>-<время>.zip` рядом с программой. Спрашивает, маскировать ли MAC/серийники в текстовых файлах (`--redact`: бинарные файлы — DTB, сэмплы flash — тогда в архив не кладутся, их список в `REDACTED.txt`). |
| **9. Показать профиль** | Сводка `ursus-profile-v1`: SoC, модель, compatible, RAM, NAND и т. д., с уровнем уверенности; пути к `profile.json` и `ursusboot-porting-report.md`. |
| **A. UBI attach** | ADVANCED, **НЕ только чтение**. Предупреждает, что attach UBI может изменить таблицу томов, записать fastmap или перенести блоки, и что для списка томов без записи лучше загрузить Linux (`ubinfo -a`). Требует `UBI ATTACH`, затем собирает U-Boot + flash с `ubi part`/`ubi read`. В профиле будет `strict_read_only: false`. |
| **N. Новая сессия** | Закрывает текущую probe-сессию и начинает новую `work/sessions/…-probe-…`. |

**Подменю «2. Профиль BootROM»:**

```
  1. Только наблюдать (ничего не отправлять)
  2. Ответить x на 'Press x' и проверить XMODEM 'C'
  3. Загрузить RAM U-Boot UrsidoRescue (только Nokia MD/MF) и собрать U-Boot/flash профиль
```

1. Пассивно пишет UART 3 минуты и отмечает маркеры (Press x, CCC, BL2/BL31/BL33, SoC).
2. Отвечает `x` и проверяет, что BootROM перешёл в приём XMODEM (`C`). Ничего не загружает.
3. Для «кирпичной» Nokia: профиль MD или MF **явно** (Auto не допускается) → стандартная процедура
   RAM U-Boot → полный probe через него. Лог загрузки кладётся в `bootrom/ram-uboot-acquire.log`.

**Что внутри bundle:** `profile.json` (каждый факт с `source` и `confidence`; high = два
независимых источника согласны, противоречия → `conflicts`, значение `null`),
`ursusboot-porting-report.md`, `ursusflasher-device-draft.json` (черновик, не для продакшена),
`hashes.sha256`, `uart.log`, `transcript.jsonl` (каждая команда: время, транспорт, ответ, результат),
каталоги `bootrom/ uboot/ linux/ flash/ mtd/ ubi/ dt/ network/ gpio/`, `README.txt`.

Итог probe — код результата (он же код выхода в командной строке):
`0` ок · `1` ошибка · `2` UART недоступен · `3` BootROM не найден · `4` U-Boot не найден ·
`5` Linux недоступен · `6` профиль неполный · `7` заблокировано нарушение безопасности.

### 8. Экспертный режим

```
Экспертный режим
  1. UART-терминал (история ↑/↓, ручной XMODEM, лог)
  2. Запустить RAM U-Boot и оставить prompt
  3. Записать существующий UBI volume из файла
  4. Записать raw range в MTD bl2/ubi
  5. Диагностика
  6. UART Shell (прозрачный терминал, ничего не отправляет сам)
  0. Назад
```

Ошибка в любом пункте эксперта возвращает в **главное** меню.

#### Эксперт 1. UART-терминал

Выбор порта → `uart.log` сессии → полноценный терминал (см.
[ниже](#uart-терминал-клавиши-и-меню)). Сам ничего не отправляет. Паролей не знает и не подбирает.

#### Эксперт 2. Запустить RAM U-Boot и оставить prompt

Профиль → стандартная процедура получения RAM U-Boot (включая проверку геометрии) → открывается
UART Shell на том же порту. Дальше вы вручную работаете в U-Boot; Ctrl+] или Ctrl+Q — назад в меню.
Полезно, когда нужна произвольная команда, которой нет в мастерах.

#### Эксперт 3. Записать существующий UBI volume из файла

1. Профиль → RAM U-Boot → `ubi part ubi` → печать `ubi info layout`.
2. Имя **существующего** тома (только `A–Z a–z 0–9 _ . -`); `ubi check <имя>` — нет тома → стоп.
   Новые тома не создаются, размеры не меняются.
3. Файл до 128 МиБ (`0x08000000`).
   Печатаются размер и SHA256.
4. TFTP + проверка в RAM → подтверждение `WRITE UBI VOLUME <имя>` →
   `ubi write` → `ubi read 0x98000000` → `crc32`.

#### Эксперт 4. Записать raw range в MTD bl2/ubi

1. Профиль → RAM U-Boot.
2. Цель `bl2` (предел `0x20000`) или `ubi` (предел `0x0FFE0000`), смещение в hex относительно начала
   цели, файл до 128 МиБ. Файл не должен выходить за границу цели.
3. Для `bl2` со смещением ≠ 0 или размером ≠ `0x20000` — предупреждение: частичная запись BL2 может
   лишить BootROM безопасной передачи управления.
4. TFTP + проверка → подтверждение `WRITE RAW <BL2|UBI> 0x<смещение>` → `mtd write` → проверка
   после записи через `0x98000000`.

`mtd write` **не стирает** перед записью: NAND можно записать только в предварительно стёртые
блоки. Если область не стёрта, выполните `mtd erase` вручную через Эксперт 2, иначе проверка CRC не
пройдёт. Карту bad-блоков этот пункт, в отличие от пункта 1, не проверяет.

#### Эксперт 5. Диагностика

То же, что [пункт 5 главного меню](#5-диагностика-nand--ubi--u-boot).

#### Эксперт 6. UART Shell

Выбор порта → `uart.log` сессии → упрощённый вариант терминала: тот же
низколатентный прозрачный режим, но без меню Ctrl+] (Ctrl+] и Ctrl+Q — выход). Никаких
автоматических `x`/Enter/Ctrl-C не отправляется — удобно просто «посмотреть, что говорит роутер».

## UART-терминал: клавиши и меню

Терминал (Эксперт 1) по умолчанию в **прозрачном режиме**: вывод устройства печатается как есть
(его можно выделять и копировать), нажатия клавиш уходят в роутер, стрелки работают через
историю самого устройства (BusyBox, U-Boot). 115200 8N1. Всё, что пришло и ушло, пишется в лог.

| клавиша | действие |
|---|---|
| **Ctrl+]** | локальное меню (в роутер не уходит) |
| **Ctrl+Q** | быстрый выход (в роутер не уходит) |
| **Ctrl+P** | вкл/выкл локальный пейджер: вывод останавливается по высоте окна, Enter — следующая страница. UART при этом продолжает читаться и логироваться (до 4 МиБ в очереди). Полноэкранные программы (`top`, `vi`, `less`) распознаются по ANSI-последовательностям — пейджер сам отключается и отдаёт им экран |
| **Ctrl+C / Ctrl+Z** | передаются в роутер как `0x03` / `0x1A` (прервать / приостановить процесс) |
| символы ≥ 0x80 | блокируются локально с предупреждением о раскладке (кириллица в команде — почти всегда ошибка). XMODEM это не касается |

**Меню Ctrl+]:**

| клавиша | действие |
|---|---|
| `l` | переключить прозрачный / **построчный** режим. В построчном строка редактируется на ПК (←/→, Home/End, Backspace, ↑/↓ — локальная история) и уходит по Enter — для устройств без своего редактора строки |
| `s` | XMODEM-отправка файла: спросит путь, попросит запустить приём на устройстве (`loadx`/`loady` в U-Boot) и нажать Enter |
| `r` | XMODEM-приём в файл (XMODEM-CRC, блоки 128/1K): спросит путь (перезапись — с подтверждением), по окончании печатает размер и SHA256 |
| `g` | показать путь к логу |
| `q` | выйти из терминала |
| Enter | вернуться в терминал |

На Windows консоль работает через `ReadConsoleInputW`: Enter, стрелки, Home/End/Delete и
Ctrl-комбинации переводятся явно; QuickEdit остаётся включённым, так что выделение мышью и
вставка работают.
