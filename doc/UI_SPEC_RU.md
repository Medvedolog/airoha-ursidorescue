## 1. Цель

Создать интерфейс UrsidoRescue, который:

- даёт понятный путь аварийного восстановления Airoha-устройств;
- поддерживает инженерный режим Probe / Porting для новых устройств;
- работает поверх общего ядра и не дублирует UART / XMODEM / NAND / UBI / FIP-логику;
- сохраняет полный технический журнал;
- отделяет исследование только для чтения от операций записи;
- одинаково применим к известным устройствам и неизвестным Airoha-платформам;
- работает на Windows и Linux без доступа в Интернет.

Архитектура:

```text
            Web-GUI (браузер)        TUI (терминал)        CLI / console
                    \                    |                    /
                     ───── application layer ─────
                  Event / Progress / Ask / Confirm / Log / Artifact
                                  ↓
                         UrsidoRescue Go Core
                                  ↓
                UART / BootROM / XMODEM / U-Boot / NAND / UBI
```

Модель продукта: **один бинарник, три лица**. Web-GUI, TUI и CLI — представления одного ядра, без собственной
hardware-логики.

## 3. Сохранение существующего поведения

UI-проект не меняет гарантии, уже работающие в 0.2.0-test17. Они переходят в core / safety policy и действуют
во всех трёх интерфейсах:

- fail-closed: после ошибки ни одной дополнительной команды записи;
- проверка после каждой записи (`mtd read` + CRC32 / `ubi read` + CRC32), проверка в RAM после TFTP;
- BL2 записывается последним, карта bad-блоков сверяется до, между и после записи;
- закреплённые SHA256 payloads;
- XMODEM: ограниченные повторы, отмена приёмником только `CAN CAN`, `CAN` от ПК только в фазе данных,
  EOT handoff доказывается следующим этапом;
- LAN/TFTP: IP ПК по маршруту, сеть U-Boot один раз за сессию, 3 попытки текущей передачи, ресинхронизация;
- Probe: allowlist команд, пассивность к неизвестному загрузчику, реквизиты stock только в памяти,
  UID 0 только по `id -u`;
- идентичность устройства не генерируется и не экспортируется.

## 4. Главное окно и раскладка

Раскладка Web-GUI и TUI одинакова по структуре (см. [ui-mockup/](ui-mockup/index.html)):

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Логотип · порт/связь · профиль/SoC · NAND · этап загрузки · RU/EN · СТОП │
├──────────────┬───────────────────────────────────────────────────────────┤
│ Меню         │ Текущий мастер / операция / профиль                       │
│ Recovery     │ полоса этапов · текущий шаг · прогресс · факты            │
│ Инструменты  │                                                           │
│ Probe        │                                                           │
│ Эксперт ▸    │                                                           │
├──────────────┴───────────────────────────────────────────────────────────┤
│ Лог UART / сессии (закреплён снизу на всю ширину)                        │
└──────────────────────────────────────────────────────────────────────────┘
```

Правила:

1. **Лог нельзя убрать полностью.** Разделитель регулируется; минимум 5 строк в Web-GUI, 1–2 строки состояния в
   TUI. Режим «развернуть лог» = терминал.
2. **Один поток.** UART и события программы идут в одном потоке; события выделены временем и цветом. Фильтр
   «Всё / UART / События» только скрывает строки, вкладок нет.
3. **Автопрокрутка с паузой.** Прокрутка вверх ставит паузу, появляется «↓ к новым строкам»; порт продолжает
   читаться.
4. **Ввод в UART** активен в терминале, в эксперте и в свободном U-Boot; во время мастера заблокирован.
5. **СТОП** всегда в верхней панели справа, далеко от поля ввода. Семантика — §17.
6. **Экспертный раздел** свёрнут по умолчанию и помечен.
7. **Прогресс мастера** — полоса этапов, а не спиннер.

## 5. Один бинарник, три интерфейса

Один обычный `go build`, `CGO_ENABLED=0`, без отдельных GUI/TUI-бинарников:

```text
ursidorescue --gui
ursidorescue --tui
ursidorescue probe ...
ursidorescue export ...
ursidorescue <CLI command> ...
```

### 5.1. Web-GUI

`--gui` поднимает локальный HTTP-сервер и открывает интерфейс в браузере системы.

Порядок запуска окна:

1. Edge / Chromium / Chrome в режиме `--app=<URL>` **с отдельным профилем** (`--user-data-dir` во временном
   каталоге сессии), чтобы не трогать профиль пользователя;
2. иначе браузер по умолчанию;
3. если открыть нельзя — сообщить причину и предложить TUI/CLI; после явного `--gui` режим молча не меняется.

Все ресурсы (HTML, CSS, JS, шрифты, иконки) встроены через `embed`. Никаких CDN и внешних загрузок.
Шрифты — встроенные с совместимой лицензией (например, OFL) или системные.

Транспорт: события и лог — Server-Sent Events; действия — `POST` с JSON. WebSocket не требуется.

### 5.2. Безопасность Web-GUI (обязательно в MVP)

Сервер умеет писать во flash, поэтому:

1. **Bind** только на `127.0.0.1` / `::1`, случайный свободный порт. `0.0.0.0` запрещён.
2. **Токен сессии**: случайный, не менее 128 бит, передаётся при запуске окна; после первого запроса
   переводится в cookie `HttpOnly; SameSite=Strict`, URL очищается.
3. **Проверка `Host`** (только `127.0.0.1:<port>`, `[::1]:<port>`, `localhost:<port>`) — защита от DNS
   rebinding.
4. **Проверка `Origin`** на всех изменяющих запросах и на SSE.
5. **CSRF-токен** в заголовке на каждый `POST`.
6. **Без CORS**; строгий `Content-Security-Policy` (`default-src 'self'`), без inline-скриптов в продакшене.
7. **Одна активная операция** и один владелец COM-порта (§9). Второе окно/вкладка подключается как наблюдатель
   (лог и статус) без права запуска операций.
8. **Закрытие окна во время операции**: ядро продолжает до безопасной точки (§17), не обрывает запись; при
   повторном открытии интерфейс подключается к той же операции. Без клиентов и без операции — сервер завершается
   через заданный таймаут.
9. Сетевой доступ с другого компьютера — вне MVP; только в Phase 2 через явный `--listen` после отдельного
   security review.

### 5.3. TUI

`--tui` — полноэкранный терминальный интерфейс на **Bubble Tea + Lip Gloss (Charm)**. Это сознательное
исключение из принципа нулевых зависимостей: pure-Go, без cgo, версии закреплены в `go.mod` / `go.sum`.

Структура та же, что в §4. Обязательная проверка на **80×24**: приоритет у текущей операции, предупреждений и
ввода; вторичные панели сворачиваются или прокручиваются. Палитра UrsusBoot; `NO_COLOR` и `TERM=dumb`
соблюдаются.

### 5.4. CLI / console

`probe`, `export` и интерактивное консольное меню сохраняются для автоматизации, CI, скриптов, аварийной
работы и обратной совместимости. CLI не становится обёрткой над HTTP.

### 5.5. Автовыбор интерфейса

Явные `--gui` / `--tui` не переопределяются. Без флага:

- Windows desktop → Web-GUI;
- Linux с графической сессией → Web-GUI;
- SSH (включая OpenSSH на Windows), headless Linux, Raspberry Pi OS Lite, Armbian minimal → TUI;
- явная CLI-команда → CLI, без открытия UI.

Определение консервативное: `DISPLAY` / `WAYLAND_DISPLAY` учитываются, но не единственный критерий;
`SSH_CONNECTION` / `SSH_TTY` → TUI. SSH-сессия никогда не открывает браузер.

### 5.6. Платформы

Windows x64, Linux x86_64, Linux ARM64 (Raspberry Pi и одноплатники). Один бинарник на OS/arch содержит все три
интерфейса.

## 6. Application layer

Обязательная прослойка между интерфейсами и ядром. Не знает о HTML, ANSI и виджетах.

```text
Event     — изменение состояния, стадия, устройство, warning/error
Progress  — determinate (current/total) или indeterminate + этап
Ask       — запрос значения/выбора/файла у оператора
Confirm   — одно подтверждение перед операцией с риском (форма — §13)
Log       — структурированный и человекочитаемый журнал
Artifact  — созданный отчёт / bundle / dump / manifest с SHA256
```

Ядро не вызывает диалоги, терминальный ввод или HTTP напрямую. Сейчас это делают `a.ask`, `a.confirm`,
`a.askPath` и `fmt.Print*` в `main.go` / `main_probe.go` — их перевод на контракт и есть основная работа этапа 1.
Пакет `probe/` уже работает через `note()` и колбэк `Ask` и подключается почти без изменений.

Одна и та же операция из любого интерфейса порождает одинаковые события, operation ID и файлы журналов.

## 7. Главное архитектурное требование

Интерфейс не выполняет низкоуровневые команды записи сам:

```text
Запрещено:  кнопка → serial.Write("mtd erase ...")

```

## 8. Сессии и журналы

Единая схема для всех интерфейсов:

```text
work/
└── sessions/
    └── 20260924-203014-an7583-7f3c/
        ├── session.json        метаданные: версия, профиль, интерфейс, результат
        ├── session.log         человекочитаемые события
        ├── uart.log            сырой UART (как нынешние *.uart.log)
        ├── operations.jsonl    структурированные операции (формат transcript.jsonl из probe)
        ├── errors.log
        ├── artifacts/          bundle, отчёты, дампы, SHA256
        └── report/
```

Переход:

- нынешние `work/recovery-*.uart.log`, `work/term-*.uart.log`, `work/probe-*` переезжают внутрь сессии;
- пакет логов для отчёта (главное меню → 6) собирает и старую, и новую схему;
- `export` и probe работают с каталогом сессии.

Session ID: `<дата>-<время>-<вид операции>-<4 hex>` (SoC пишется в `session.json`, а не в имя: при создании
сессии он ещё неизвестен). Operation ID: `op-<дата>-<время>-<сценарий>-<4 hex>`.
Оба попадают во все логи, события, ошибки и отчёты.

Структурированная запись:

```json
{"ts":"2026-09-24T20:30:14.431+03:00","level":"info","op":"op-20260924-203014-probe-19aa",
 "operation":"probe_mtd","transport":"uart","stage":"uboot","risk":"READ_ONLY","result":"success"}
```

## 9. Порт и подключение

**Владелец порта — сессия application layer.** Мастера, терминал и probe получают открытый порт из сессии и не
открывают его сами (сейчас это делает `acquireRAMUBoot`). Одновременно порт используется одной операцией;
терминал во время мастера — только наблюдатель.

Экран подключения:

- список портов (Windows — `QueryDosDeviceW`, Linux — `/dev/ttyUSB*`, `ttyACM*`, `ttyAMA*`, `ttyS*`);
- *желательно:* friendly name и VID/PID адаптера без cgo (SetupAPI через syscall на Windows, `/sys` на Linux);
- 115200 8N1, flow control none по умолчанию; RTS/DTR — в Advanced;
- состояние соединения и определённая стадия загрузки;
- кнопки Refresh, Connect, Disconnect, Auto-detect.

Auto-detect: перечислять порты, замечать появление нового USB-UART, предлагать его, **не подключаться
автоматически** к неизвестному порту, не привязывать модель к номеру COM.

Индикатор стадии: BootROM / Preloader-BL2 / U-Boot / Linux / Unknown и уверенность High / Medium / Low /
Unknown.

Linux без прав на порт: понятная диагностика; нельзя запускать `sudo`, менять группы или udev.

## 13. Подтверждение по классу риска

Правило: **одно подтверждение на операцию, в одном диалоге, после автоматического preflight**. Цепочек
диалогов нет. Форма зависит от класса:

| Класс | Подтверждение |
|---|---|
| READ_ONLY | нет |
| NON_PERSISTENT | нет или кнопка |
| SETTINGS_CHANGE | кнопка; в тексте — что именно изменится и что это останется после операции |
| UBI_METADATA | ввод фразы |
| WRITE, ERASE, IDENTITY_CHANGE | ввод фразы |
| MANUAL | нет; постоянная пометка «ручной режим, safety policy не применяется к вводу» |

Фразы одинаковы во всех языках и интерфейсах (как сейчас). Кнопка «Выполнить» активна только после точного
совпадения. В CLI без интерактива операции классов WRITE/ERASE/UBI_METADATA/SETTINGS_CHANGE не выполняются.

---

## 14. Классы риска

```text
READ_ONLY        только чтение
NON_PERSISTENT   только RAM / временное состояние, исчезает после reset
SETTINGS_CHANGE  меняет настройку stock/устройства без raw-записи flash (например, включение FTP)
UBI_METADATA     может изменить служебные данные UBI (ubi part: auto-resize, fastmap)
WRITE            запись во flash
ERASE            стирание flash
IDENTITY_CHANGE  затрагивает MAC / serial / GPON / ключи
MANUAL           ручной ввод оператора в UART
```

UI-уровни: INFO / WARNING / DANGER / BLOCKED. Красные предупреждения не используются для чтения.

## 15. Preflight Summary

Пример для реальной разметки Nokia MD/MF:

```text
Устройство:   Nokia XG-040G-MF · Airoha AN7583
Операция:     Починить загрузку (FIP)
Цель:         UBI-том "fip" на разделе ubi (0x00020000–0x10000000)
Длина:        324 908 байт
Файл:         recovery-safe-u-boot.fip · SHA256 7b56…d782
Проверки:     заголовок TF-A FIP ToC ✓ · размер в пределах ✓ · том fip существует ✓
Класс риска:  WRITE
Данные устройства затронуты: нет
```

Для стока дополнительно: размер `mtd16` ровно `0x0EBA0000`, происхождение BL2, bad-блоки в безопасном окне,
тест TFTP до записи. При расхождении профиля и железа — WARNING и блокировка (§42).

## 16. Проверка образов

Размер, SHA256, формат/сигнатура (FIP ToC, FIT, UBI, gzip), тип содержимого, допустимый размер цели,
совместимость с профилем, защищённые диапазоны, пересечение с областями личности. Очевидные несовместимости
(FIP → rootfs, OpenWrt BL2 вместо стокового) блокируются.

---

## 17. Отмена и кнопка СТОП

СТОП = «завершить до ближайшей безопасной точки, дальше ничего не писать». Каждая операция объявляет:
Cancelable / Not cancelable / Cancelable at safe checkpoint.

| Сценарий | Когда отмена немедленная | Безопасная точка | Когда отменить нельзя |
|---|---|---|---|
| BootROM / XMODEM | ожидание BootROM, до начала передачи | фаза данных: `CAN CAN CAN` | после ACK последнего блока, пока не доказан следующий этап |
| Вернуть сток | до `mtd erase ubi` | между частями IBU, после readback части | от `mtd erase bl2` до проверки BL2 |
| Залить весь NAND | до `mtd erase ubi` | между частями, после readback | от `mtd erase bl2` до проверки BL2 |
| Починить FIP | до `ubi write` | — | `ubi write` → `ubi read` → CRC |
| Эксперт UBI-том / raw MTD | до записи | — | запись и readback |
| Загрузить ITB | до `bootm` | — | после `bootm` управление у ядра Linux |
| Probe | в любой момент | — | включение FTP через Web: дождаться ответа |
| TFTP-передача | в любой момент (сервер отменяется, порт освобождается) | — | — |

Остановка на безопасной точке фиксируется в отчёте как Cancelled с указанием, что записано и проверено.

---

## 18. BootROM / XMODEM

Этапы: ожидание BootROM → `Press x` → `CCC` → передача preloader → второй приёмник → передача FIP → RAM U-Boot.
Показывать прогресс, байты, скорость, повторы, номер блока, время, состояние отмены, отдельную отметку «EOT ACK
не получен, доказательство — следующий этап».

---

## 19. Probe / Porting

Главный сценарий — **полный автоматический probe только для чтения**; отдельные слои: BootROM, U-Boot, Linux,
Flash / MTD / UBI, Device Tree, Network / PHY / Switch; экспорт bundle.

Баннер режима — информационный, не модальный, и **честно меняется**:

- `READ-ONLY` — по умолчанию;
- `SETTINGS CHANGED` — если оператор включил FTP через stock Web;
- `NOT READ-ONLY: UBI ATTACH` — в режиме UBI attach.

Блокировка команд — технически в API probe (allowlist), а не в UI.

Этапы probe со статусами Pending / Running / Success / Partial / Skipped / Failed. Сводка результата: SoC и
уверенность, flash, число MTD и UBI, PHY, DTB, Linux, UID0, конфликты, предупреждения. Кнопки: профиль,
конфликты, логи, bundle, отчёт UrsusBoot, черновик UrsusFlasher.

---

## 20–21. Перенос личности и Identity Editor — Phase 2

Использование чужого бэкапа с сохранением/переносом личности и редактор MAC / serial / GPON **не входят в MVP**.
Это отдельное ТЗ после security review: правило семейства — личность не генерируется и не переносится между
устройствами. В MVP: области личности выявляются, маркируются и показываются как предупреждение в preflight.

## 22–30. Просмотрщики (Probe)

- **Profile Viewer** `ursus-profile-v1`: Overview, SoC, Boot chain, Flash, MTD, UBI, U-Boot, DT, Network, GPIO,
  Linux, Capabilities, Warnings, Conflicts, Artifacts.
- **MTD Viewer**: таблица Name / Offset / Size / Source / Confidence; конфликтующие источники не скрываются.
- **UBI Viewer**: device, MTD, PEB/LEB, offsets, тома, reserved, used, confidence. Без create/remove/write.
- **Confidence**: High / Medium / Low / Unknown с источниками («High — подтверждено U-Boot и Linux»).
- **Conflict Viewer**: значения каждого источника, `Selected: none`, «требуется ручной анализ». Источник не
  выбирается молча.

Графическая карта flash, Boot Chain, Device Tree, Network topology — Phase 2.

## 31. UART Console

## 32. Command Inspector

Для каждой команды автоматизации: transport, stage, command, класс риска, timeout, result, operation ID.
Пароли и реквизиты не показываются никогда (как в `transcript.jsonl` сейчас).

## 33. Ошибки

Короткое описание → технические детали → рекомендуемое действие; кнопка Details: код ошибки, стадия,
transport, команда, сырой ответ, контекст. Сообщение `[STOP]` с пометкой «дальнейших write/erase не было»
сохраняется.

## 34. Результат операции

Отдельно: Write / Read-back / Hash verification / Boot test. Без реального boot test нельзя писать «устройство
восстановлено». Статусы: Success, Partial, Failed, Cancelled, Skipped, Not verified. Если процент неизвестен —
этап или неопределённый прогресс, а не фиктивные 0–100%.

## 35. Drag & Drop и File Inspector

Drop файла (FIP, прошивка, дамп, бэкап) — только анализ, запись не стартует. Inspector: имя, размер, SHA256,
формат, предполагаемая цель, совместимость, метаданные, предупреждения.

---

## 36. Отчёты и экспорт

Локальная история сессий (дата, устройство, режим, результат), без облака. Экспорт: полная сессия, porting
bundle `ursus-probe-<vendor>-<model>-<soc>-<date>.zip`, отчёт восстановления, только логи. SHA256 на все
артефакты, `hashes.sha256` в bundle. По умолчанию без реквизитов и ключей; «Redact device identity» — как
нынешний `--redact`.

## 37. Профили устройств

Auto detect / известный профиль / Unknown generic Airoha. Известный профиль не отменяет обнаружение железа.
Черновик `ursusflasher-device-draft.json` визуально отделён от production-профилей. Статусы профиля:
Built-in, User supplied, Generated draft, Verified, Experimental.

## 42. Расхождение профиля и железа

Операции классов WRITE / ERASE / UBI_METADATA / IDENTITY_CHANGE блокируются до разрешения конфликта. Probe и

## 43. Длительные операции и производительность лога

XMODEM, ожидание BootROM, чтение flash, probe, архивы и SHA256 выполняются вне UI-потока. Лог: буферизация,
ограничение частоты отрисовки, кольцевой буфер в интерфейсе (порядка 20 000 строк), полная запись в файл
независимо от UI.

## 44. Сбои и переподключение

При падении интерфейса сохраняются session log, uart.log, состояние операции и crash report. Ядро не зависит от
окна. Reconnect порта без потери probe-сессии — желательно; для записи автоматическое продолжение только там, где
алгоритм это гарантирует.

## 45. Тема, DPI, доступность

MVP: тёмная тема в палитре UrsusBoot. Светлая и системная — Phase 2. Клавиатурная навигация, видимый фокус,
high-DPI и масштаб Windows 125/150/200%, цвет — не единственный признак состояния, минимальное окно 1280×720,
прокрутка вместо обрезания.

---

## 46. Advanced и Debug

Advanced (по-прежнему под safety policy): произвольное чтение раздела, чтение RAM, ручной профиль, свои адреса и
смещения, raw-консоль, FIP-парсер. Debug: поток событий, operation ID, решения парсеров, источники уверенности,
кадры транспорта. Debug не разрешает запись.

## 47. Структура исходников

Цель:

```text
cmd/ursidorescue   main, выбор интерфейса
app/               application layer, сессии, operation ID
core/              recovery, safety policy
transport/         serial, xmodem, tftp
probe/             (уже отдельный пакет)
profile/  report/
```

Переход **поэтапный**: сейчас всё, кроме `probe/`, в `package main`. Каждый перенос — отдельный шаг с зелёными
`go vet` / `go test` и неизменным консольным поведением. Одного большого переезда нет.

## 49. Порядок разработки (часть ТЗ)

### Этап 1 — Application layer
1. Контракт Event / Progress / Ask / Confirm / Log / Artifact.
2. Сессия владеет портом; мастера получают порт из сессии.
3. Схема `work/sessions/<id>/`, operation ID.
4. Консольное поведение не меняется; все тесты зелёные.

### Этап 2 — TUI
Bubble Tea + Lip Gloss; выбор порта, connect/disconnect; статус; лог UART; навигация Recovery/Probe; полный
probe; прогресс и подтверждения по §13; 80×24; Linux x86_64 и ARM64; корректная работа по SSH.

### Этап 3 — Web-GUI, сначала только чтение
Встроенный сервер с безопасностью §5.2; окно app-mode; лог и терминал; диагностика; полный probe; профиль,
отчёты, bundle.

### Этап 4 — Web-GUI, мастера записи
BootROM/XMODEM, FIP, сток, NAND, preflight, подтверждение по §13, readback, отмена по §17.

### Аппаратная матрица
Windows x64, в том числе без драйвера видеокарты и в ВМ; Linux x86_64 desktop; Linux x86_64 по SSH;
Raspberry Pi / ARM64 в TUI. CI и mock PASS не заменяют HW PASS.

## 51. Критерии приёмки MVP

1. Один source tree → один бинарник на OS/arch, без cgo.
2. Бинарник содержит Web-GUI, TUI и CLI.
3. `--gui` / `--tui` выбирают режим явно и предсказуемо; автовыбор — по §5.5; SSH не открывает браузер; CLI-команды
   не запускают UI.
4. Web-GUI: только loopback, случайный порт, токен, проверка Host/Origin, CSRF, CSP; ресурсы и шрифты встроены,
   работа без сети.
5. Закрытие окна во время записи не обрывает операцию до безопасной точки; повторное открытие подключается к ней.
6. TUI работает на 80×24 и на Linux ARM64 / Raspberry Pi.
7. Выбор порта и connect/disconnect без CLI; порт принадлежит сессии; одна операция одновременно.
8. Лог UART виден во всех интерактивных режимах и пишется в `work/sessions/<id>/uart.log`.
9. Стадия BootROM / U-Boot / Linux и SoC определяются там, где это умеет ядро.
10. Все интерфейсы используют общий application layer и одинаковую семантику событий.
11. Операции записи показывают preflight; подтверждение — одно, форма по §13; фразы сохраняются для
    WRITE / ERASE / UBI_METADATA.
12. Probe технически не выполняет запись flash; баннер режима честно отражает FTP и UBI attach.
13. Отмена соблюдает безопасные точки §17.
14. Полный probe создаёт `ursus-profile-v1`; bundle и отчёты не зависят от интерфейса.
15. Конфликты источников не скрываются; области личности выделены.
16. Все операции имеют operation ID; артефакты — SHA256.
17. Сбой интерфейса не уничтожает логи.
18. Длительные операции не блокируют интерфейс.
19. Расхождение профиля блокирует запись, но не probe.
20. Все гарантии §3 сохранены и покрыты тестами.
21. CI PASS, mock PASS и HW PASS отображаются раздельно.

## 52. Роли в экосистеме

- **UrsidoRescue** — доступ к BootROM, UART/XMODEM, аварийное восстановление, разведка и сбор данных для
  портирования, офлайн-анализ.
- **UrsusBoot** — постоянный recovery-загрузчик в роутере.
- **UrsusFlasher** — установка, миграция, бэкапы, политика устройств.
- **MedveFlasher** — переход стока Nokia на OpenWrt без UART.

## 53. Главный принцип

Интерфейс делает сложные операции понятнее, но не скрывает реальное состояние устройства и не подменяет
инженерную диагностику декоративной автоматизацией.

```text
One binary. Three faces. One application layer. One core. One safety policy.

Web-GUI ─┐
TUI ─────┼→ Application layer → UrsidoRescue Core → hardware
CLI ─────┘
```
