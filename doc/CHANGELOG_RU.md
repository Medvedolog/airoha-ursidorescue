# История изменений UrsidoRescue (полная, реконструированная)

[English version](CHANGELOG_EN.md) · [Оглавление](README.md)

Этот файл восстановлен с самого начала проекта по следующим источникам:

- история git этого репозитория (все коммиты, их тексты и диффы);
- теги `v0.2.0-test*` и опубликованные pre-release на GitHub;
- разделы `STATUS.md` каждой версии;
- исходный код на момент каждой версии (номера меню, лимиты, поведение);
- соседние репозитории семейства Ursus (MedveFlasher, UrsusBoot) — для предыстории.

То, что происходило до первого коммита этого репозитория, известно только по упоминаниям в
`STATUS.md` и коде 0.2.0-test2; такие разделы помечены **(реконструкция)**.

**Обозначения статуса:**

- **simulation PASS** — тесты и симуляция прошли;
- **simulation candidate** — кандидат, ещё не прошедший полный прогон;
- **HW PARTIAL** — часть функций проверена на железе;
- **HW HOLD / PENDING** — на железе не проверено.

Сборка и CI не заменяют проверку на железе.

через CI.

## Не выпущено

- Добавлена папка `doc/` с документацией на русском и английском: о проекте и семействе Ursus,
  руководство оператора, подробное описание всех меню, архитектура, эта полная история изменений.
- Добавлен `README.ru.md` — русская версия главного README; на него ссылается английский `README.md`.
- Титульные `README.md` / `README.ru.md` оформлены заново: шапка с медведем и бейджами, цель и
  возможности, принципы, быстрый старт, ссылки на документацию. Таблица происхождения payloads
  перенесена в ARCHITECTURE.
- `PROBE.md`: номер пункта главного меню Porting Collector исправлен на 7. Номер 8 устарел с test5.
- Утверждено ТЗ v3 на единый интерфейс Web-GUI / TUI / CLI (`doc/UI_SPEC_RU.md`) и добавлен
  HTML-макет Web-GUI (`doc/ui-mockup/`).
- **Этап 1 ТЗ — application layer** (консоль ведёт себя как раньше):
  - пакет `app`: контракт Event / Progress / Ask / Confirm / Output / Artifact, классы риска,
    подтверждение по классу (фраза обязательна для WRITE / ERASE / UBI_METADATA);
  - ядро сообщает и спрашивает только через UI; консоль — одна из реализаций; тест-страж на `go/ast`;
  - каталог операций и `RunOperation`: каждая операция в своей сессии
    `work/sessions/<дата>-<время>-<вид>-<hex>/` (`session.json`, `session.log`, `uart.log`,
    `operations.jsonl` с каждой командой U-Boot, `errors.log`), operation ID на всех событиях;
  - порт принадлежит `PortOwner` и сдаётся операции в аренду, одна операция одновременно;
  - UART-логи и нарезка образов переехали в каталог сессии; пакет логов и `export` находят и
    старые файлы в `work/`.
- **СТОП в ядре:** режимы «сразу / в безопасной точке / недоступно» (`CancelState`) по фазам каждой
  операции; XMODEM в фазе данных прерывается `CAN CAN CAN`, после последнего ACK остановка
  недоступна до доказанного следующего этапа; в «недоступной» фазе запрос отклоняется, а не
  откладывается. Подтверждение показывает класс риска, действия по порядку и границу остановки.
- В консоли Ctrl+C во время операции — это СТОП (второй Ctrl+C за 3 с — принудительный выход);
  вне операции и в UART-терминале поведение прежнее.
- **Этап 2 ТЗ — TUI** (`--tui`, Bubble Tea + Lip Gloss): те же меню, что в консоли; лог UART и событий
  всегда на экране (≈35 %, фильтр, прокрутка, перенос строк); диалоги подтверждения по §13 с классом
  риска, действиями и границей остановки; выбор и подключение порта; СТОП по `s` / Ctrl+C с надписью
  от ядра; UART-терминал и Shell на весь экран с возвратом в TUI; проверка раскладки 80×24 в тестах.
  Без `--tui` запускается прежнее консольное меню.
- TUI по первым отзывам: зоны экрана разделены (верхняя и нижняя плашки, заголовки-линейки, плашка лога,
  вертикальная черта у лога); у каждого пункта меню — описание: что делает, что нужно, риск; вопросы «да/нет»
  и короткие варианты (`bl2/ubi`, reset / остаться) — кнопками, списки — стрелками с подсветкой, по умолчанию
  выбран вариант из `[1]`; горячие клавиши работают в русской раскладке и через F2/F3/F4/F10; длинные строки
  переносятся по словам. Для этого `AskRequest` получил `Quick` и `Default` — консоль их не показывает.
- TUI, по ревью ветки:
  - окно порта (`p`) при пустом списке портов больше не пустое: пишет «порты не найдены» и даёт ввести имя
    вручную, как консоль;
  - probe с ненулевым кодом (нет UART, BootROM/U-Boot/Linux, неполный профиль) больше не показывается
    зелёным «Готово»: итог «НЕ ПОЛНОСТЬЮ» с кодом и причиной, сессия записывается как failed; вывод консоли
    не изменился;
  - длинное подтверждение не обрезается: строка ответа (фраза и поле ввода или кнопки) закреплена внизу,
    текст над ней прокручивается ↑/↓ с указателем «строки N–M из K».
- **TUI — режим по умолчанию.** Без флагов открывается TUI; прежнее текстовое меню — `--console` и
  автоматический запасной вариант, если TUI не может работать (не терминал, `TERM=dumb`, ошибка). Язык — из
  языка Windows (в Linux — из локали), клавиша `l` переключает его в TUI.
- TUI, по отзыву с Windows: события в логе раскрашены как в консоли и UrsusFlasher (метки этапов янтарные,
  PASS зелёные, ошибки бордовые), вывод роутера — тёмно-салатовый; в бегущем логе нет времени (оно в файлах
  логов), в панели операции время — отдельной бледной колонкой, текст не скачет; из верхней строки убран
  «op …xxxx», похожий на обрывок контрольной суммы.
- Адрес ПК для TFTP: годится любой 192.168.1.2–.254, не только .254. Если адреса нет, программа до 20 с ждёт
  линк (Windows прячет статический адрес карты без линка, пока роутер не поднял порт), затем объясняет, что
  настроить, и предлагает «Повторить поиск / Ввести адрес / Отмена»; введённый адрес проверяется (подсеть, не
  .1, назначен карте этого ПК), при ошибке вопрос повторяется, а не обрывает операцию.
- TUI: общий прогресс записи стока и полного NAND («часть N из M, затем BL2») отдельной широкой строкой над
  текущей передачей; в консоли он не выводится — там каждая часть и так своей строкой.
- TUI: статусы в логе заметнее: успех — жирный ярко-зелёный с «✓», предупреждение — «!», ошибка — жирный
  бордовый с «✗»; шаги программы — светлым, заметки и вывод роутера — тёмно-салатовым. Шапка залита фоном до
  кнопки СТОП.
- Занятый COM-порт: окно говорит, какой порт занят и кем он может быть занят, и что сделать; кнопки
  «Повторить / Другой порт / Отмена» (раньше «Отмена» ошибочно подписывалась «Нет»); консольные буквы `(r)` и
  `[1]` в TUI не показываются — вместо них кнопки и список.
- Занятый другой программой COM-порт — не ошибка: «занят другой программой, закройте её» и выбор
  «повторить / другой порт / отмена» (консоль и TUI). В Linux занятость определяется по `flock`.
- TUI и тексты меню, по второму ревью:
  - после неполного probe итог говорит, что реально произошло: «команд записи во flash не отправлялось»,
    «выполнялся ubi part — UBI мог изменить метаданные», «на stock-прошивке включён FTP», «RAM U-Boot только в
    памяти» — из фактического результата, а не одной фразой для всех;
  - «Диагностика NAND / UBI / U-Boot» переименована в «Диагностика NAND / MTD / U-Boot» (консоль, TUI, MENU):
    она не подключает UBI и томов не показывает; описание говорит, куда идти за томами;
  - пункт 2 главного меню — «Восстановить FIP, если UBI цел» (было «Починить загрузку OpenWrt / заменить FIP»);
  - описание полного probe: flash не записывает, включение FTP спросит отдельно;
  - в TUI нет повторной «Диагностики» в «Эксперте» (в консоли номера пунктов не менялись);
  - на экране итога — ID сессии и операции, полный путь к логам — в логе;
  - на 80×24 описание пункта всегда целиком: в режиме ожидания лог сжимается до 3 строк, медведь только в
    свободном месте.
- TUI: пустая строка отделяет вкладки от списка; подсказки навигации перенесены под список меню (если
  помещаются; те же клавиши всегда в нижней строке); нижняя строка подсказок — тёмно-салатовая, как рамка лога.
- TUI: лого — голова медвежонка с подмигиванием и улыбкой (большая 8 строк, маленькая 5), подпись
  «семейство Ursus · Bearborn utility»; на большом экране пункты меню через строку, жирные, с подсказкой под
  названием; панель лога и обычный текст лога — тёмно-салатовые, цветные только статусы.
- «Вернуть сток»: вместо «бэкап MedveFlasher» — какой бэкап принимается: файл mtd16 или all_flash (.bin или
  .bin.gz) или каталог с mtd16.bin(.gz); так же сформулированы вопрос пути и сообщение о найденных файлах.
- TUI: лого — сидящий подмигивающий плюшевый медвежонок из полублоков `▀▄█` (по мотивам ASCII-арта): уши,
  открытый глаз и подмигивание, нос, лапки, пятки с подушечками; большой (12 строк) и маленький (6 строк)
  для 80×24.
- TUI: лого — подмигивающий ASCII-медведь с надписью UrsidoRescue и версией: большой в левом верхнем углу,
  если хватает высоты, иначе маленький в свободном углу меню; меню и описание он не вытесняет.
- Porting Collector: приглашение `Username:` / `User:` распознаётся как вход (раньше только `login:`); если
  последняя строка не похожа на известное приглашение, probe пишет это, а не ждёт молча до тайм-аута.
- Пункты меню «Портирование» сообщают о ходе работы через application layer — консоль выводит то же, что
  раньше; литеральный `\n` в тексте UBI attach заменён переводом строки.
- Go 1.24 (нужен модулям Charm); `probe`: строки `Info` без неконстантного формата (требование `go vet`).
- Этап 1 (application layer, СТОП, Ctrl+C) прошёл проверку на железе по `doc/HW_SMOKE_STAGE1_RU.md` —
  **HW smoke PASS**.
- ТЗ v3.1 и макет: состояния СТОП, выбор порта, ID на экране, баннеры Porting, экраны ожидания
  BootROM и результата, компактный режим, без внешних шрифтов.
- ТЗ v3.2: слой бэкендов и лестница деградации (persistent UrsusBoot Web/UART → RAM RECOVERY_SAFE →
  BootROM), детектор «кто на том конце» как отдельный этап. ABOUT и ARCHITECTURE уточняют: RAM FIP — ванильный
  OpenWrt U-Boot по контракту RC18, собранный конвейером UrsusBoot, без кода UrsusBoot.
- Документация и `PROBE.md` обновлены до test17: сеть и пререквизиты LAN, цветной вывод, EOT,
  stock LAN assist, `--stock-lan-assist`, Telnet-only passive plan и повторное чтение поздних паролей.
- **Эксперт 7 / TUI «Эксперт → Установить UrsusBoot (UART)»** — постоянная установка UrsusBoot
  0.1.0-alpha5-t67 на MD и MF только через UART и RAM U-Boot, для стоковой и UBI-разметки.
  Кандидат собирается из текущего содержимого устройства: оно читается по UART (`md.l` кусками
  по 64 КиБ, каждый сверяется `crc32` устройства; в RAM U-Boot нет `tftpput`) и сохраняется в
  сессии как бэкап. MD — закреплённый t67 update.fip на `0x800` живой загрузочной области; MF —
  замена только BL33 в живой FIP (порт UrsusFlasher 0.2.67). Префикс BootROM и stock env —
  байт-в-байт; пишутся только изменённые блоки, BL2 последним; на UBI — только том `fip`

  в `payloads/`; `--selftest` проверяет и их. Запись тома fip в «Восстановить FIP» вынесена в
  общий помощник (команды те же).

- TUI, по разбору ревьюера: UART-консоли больше не «проваливаются» в чёрный экран. Raw-backend
  (`tea.Exec`, `consoleRaw`, XMODEM, детектор fullscreen ANSI) не менялся; новый `term_chrome.go`
  рисует поверх него шапку и строку клавиш UrsidoRescue через ANSI scroll region, плашку при входе,
  уступает экран `top`/`vi`/bootmenu и возвращается после них. Порт для консолей выбирается в
  диалоге TUI до входа. `--console` выводит всё как раньше.
- Названия: «UART Shell» → «Прозрачная UART-консоль», «UART-терминал» → «UART-терминал + XMODEM»
  (обе стороны). Эксперт в TUI упорядочен по риску, риск (`MANUAL` / `RAM only` / `WRITE` /
  `RAW WRITE` / `ERASE`) — прямо под названием пункта. Help bar показывает F-клавиши; шапка во
  время операции — её имя и фазу (`READ 37%`, `2/6`).
- Установка UrsusBoot: общий прогресс по 6 этапам (RAM U-Boot и разметка → чтение → проверка и
  сборка → TFTP → запись → итоговая сверка), перед чтением — что именно читается и что запись ещё
  не началась; на стоке после поблочной записи вся область 0x80000 читается обратно и сверяется CRC32.
- Подпись маленького медведя больше не сдвигает разделитель на 80 колонках.
- Рамка UART-консоли, по ревью be131bf: для неё свой потоковый разбор управляющих
  последовательностей (пейджер оставил старый детектор). Alternate screen снимает рамку строго до
  парного выхода; bootmenu — скрытый курсор + очистка до показа курсора; одиночные `ESC[H`,
  `ESC[2J`, `ESC[?25h` рамку больше не снимают (`clear` в shell оставляет курсор в области вывода,
  полосы перерисовываются). Разрезанная между чтениями последовательность выхода больше не стирает
  следующее приглашение; рамка следит и за изменением ширины окна.
- Новая операция в TUI начинается без общего прогресса предыдущей.
- Пути к файлам: до трёх недавних путей на операцию за запуск (номер или ↑↓), «Обзор…» — окно
  выбора файла Windows (comdlg32, без cgo) или zenity/kdialog в Linux. Путь запоминается сразу после
  проверки. Для бэкапа стока — ещё и выбор каталога: окно проводника в режиме папки
  (IFileOpenDialog, FOS_PICKFOLDERS, через COM без cgo), в Linux — `zenity --directory` / kdialog.
- Протокол проверки на железе `doc/HW_SMOKE_STAGE2_RU.md`: рамка UART, alternate screen, bootmenu,
  ширина окна, «Обзор» файла и каталога, недавние пути, затем установка UrsusBoot. Статус сборки
  `404b3b5`: CI PASS / HW PENDING. В руководстве уточнено: каталог бэкапа должен содержать mtd16,
  остальные mtd0…mtd15 необязательны.
- **Ложная ошибка «CRC после записи не совпал» при восстановлении стока (найдено на железе).** Устройство
  посчитало верный CRC (`==> 15f1f21c` = ожидаемому), но программа сверяла вывод раньше, чем он пришёл:
  `promptPresent` принимал `=>` в конце строки `crc32 … ==>` за приглашение U-Boot, если чтение UART
  обрывалось сразу после стрелки. Теперь приглашение засчитывается только в начале строки (или после
  ANSI), регрессионный тест на этот разрыв добавлен. Кроме того, расхождение CRC после записи сначала
  дважды перепроверяется повторным чтением (только чтение) и лишь потом считается ошибкой.
- TUI по отзыву с Windows: полоса лога залита до правого края; F5 / h (р) скрывает лог до его полосы; в
  шапке название операции целиком или только шаг, без обрезков; кнопка СТОП — одна («■ СТОП: s / Ctrl+C»),

**Исправлено — XMODEM EOT handoff:**

- Если **все блоки данных подтверждены**, отсутствие ACK на EOT само по себе больше не фатально.
  Успех доказывается следующим этапом:
  - после preloader — появлением второго приёмника XMODEM BootROM (`CCC`);
  - после FIP — устойчивым приглашением RAM U-Boot.

  успешный handoff».
- Ответ на EOT разбирается с учётом этапа:
  - ACK — окончательное подтверждение;
  - NAK — повторить EOT;
  - ASCII `C` или любой загрузочный текст — это уже вывод следующего этапа, EOT больше не
    повторяется. Так буква `C` внутри слов вроде `NOTICE` не принимается за запрос CRC.
- EOT повторяется не более **3 раз** с ожиданием 1,5 с. Повтор идёт только пока вывода следующего
  этапа нет.
- `CAN CAN CAN` отправляется только при сбое **фазы данных**. После ACK последнего блока он не
  отправляется никогда: принимающая сторона может уже исполнять переданный образ.
- При разборе ответа на блок ACK имеет приоритет над шумом `C`/NAK в том же чтении UART.
- Байты UART, полученные во время EOT, сразу передаются разборщику следующего этапа. Баннер и
  приглашение U-Boot, пришедшие в том же чтении, не теряются, и автозагрузку можно прервать.
